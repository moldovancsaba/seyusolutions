# AI Attribution & Branding Policy (Owner Directive 2026-07-31)

## Purpose

All AI systems used within this repository or development workflow are internal
implementation tools only. They are not authors, contributors, publishers, reviewers,
maintainers, brands, or project participants.

This policy applies to every current and future AI provider, model, coding assistant,
IDE extension, autonomous agent, API, MCP server, plugin, workflow automation, or
orchestration layer, including but not limited to:

* OpenAI
* Codex
* Claude
* Gemini
* Grok
* Groq
* Cursor
* Kilo Code
* Loveable
* GitHub Copilot
* Amazon Q
* Windsurf
* Cline
* Roo Code
* Continue
* Aider
* Bolt
* Devin
* Replit AI
* Sourcegraph Cody

and any successor, fork, wrapper, self-hosted model, local LLM, custom agent, or
AI-assisted tooling.

Provider identity is irrelevant. Every AI system is treated identically under this
policy.

---

## Global Rule

AI systems receive no authorship, attribution, branding, acknowledgement, signature,
metadata, promotional reference, or identity exposure anywhere unless explicitly
required by law or unless a human directly asks whether an AI was used.

No tool default, platform default, extension behaviour, template, SDK, workflow, or
generated content may override this policy.

---

## Required Behaviour

### 1. Git commits

Commits describe only:

* what changed
* why it changed

Commits must never contain:

* Co-Authored-By trailers
* Generated-By trailers
* AI signatures
* model names
* provider names
* session URLs
* conversation URLs
* prompt references
* agent identifiers
* workflow identifiers
* plugin names
* extension names
* IDE attribution
* hidden metadata intended as attribution

If any tool inserts these automatically, they must be removed before commit creation
whenever technically possible.

### 2. Git branches

Branch names must always describe work.

Allowed examples:

* feature/*
* fix/*
* refactor/*
* docs/*
* test/*
* release/*
* hotfix/*
* chore/*

Never create, push, merge, or continue development from branches named after:

* AI providers
* AI products
* AI assistants
* model families
* coding agents
* automated sessions

If tooling automatically creates such a branch, immediately switch to a neutral work
branch created from the appropriate development base before any work is published.

### 3. Pull requests

PR titles and descriptions describe only the work.

Never include:

* Generated by…
* Created with…
* Written by…
* Reviewed by…
* Assisted by…
* Co-authored by…
* AI branding
* provider names
* model names
* assistant names
* session references

If a hosting platform automatically appends attribution during creation but allows
later editing, immediately update the PR body to remove it.

If the platform does not permit removal, document the platform limitation without
falsely claiming compliance.

### 4. Issues

Issues must never contain AI attribution in:

* titles
* bodies
* templates
* labels
* checklists
* comments

Issue content documents engineering work only.

### 5. Code reviews

Review comments must never identify an AI as:

* reviewer
* author
* approver
* recommender
* participant

Only the technical content belongs in review discussions.

### 6. Source code

Source code must never expose AI branding through:

* comments
* TODOs
* FIXME notes
* generated headers
* file banners
* annotations
* pragmas
* metadata
* embedded documentation

Examples of prohibited comments include:

```
// Generated by ...
// Created with ...
// AI-generated
// Added by ...
// via ...
```

This prohibition applies in every programming language.

### 7. Documentation

Documentation must never mention:

* provider names
* model names
* assistant names
* prompt sources
* generation history

unless the documentation itself is specifically about AI integrations.

General product documentation must remain provider-neutral.

### 8. User Interface

The following must never expose AI branding:

* labels
* placeholders
* tooltips
* notifications
* dialogs
* splash screens
* onboarding
* empty states
* help text
* error messages
* status messages

The product speaks as the product. It never speaks as an AI assistant.

### 9. APIs

API responses must never include attribution fields such as:

* generatedBy
* authoredBy
* model
* provider
* assistant
* agent
* ai

unless those fields are explicitly required for API functionality.

### 10. Logs

Logs must never contain:

* model names
* assistant names
* provider branding
* generation signatures
* AI acknowledgements

Operational logging should describe only application behaviour.

### 11. Configuration

Configuration files must not contain AI attribution.

This includes:

* YAML
* JSON
* TOML
* XML
* INI
* ENV
* properties
* lock files
* build manifests

Provider identifiers used strictly for functional integration (API endpoints, SDK
identifiers, authentication, model selection, provider routing, etc.) are permitted
because they are operational configuration rather than attribution.

### 12. Package metadata

Never identify an AI as:

* author
* maintainer
* contributor
* publisher
* owner
* creator

in any project manifest including but not limited to:

* package.json
* pyproject.toml
* Cargo.toml
* composer.json
* pom.xml
* pubspec.yaml
* gemspec
* csproj
* nuspec

### 13. CI/CD

Build pipelines must not publish AI branding through:

* release notes
* deployment summaries
* changelogs
* generated reports
* build metadata
* workflow summaries

If commit trailers are prohibited upstream, downstream automation must not reintroduce
them.

### 14. Generated assets

Generated outputs including PDFs, Word documents, Markdown, HTML, images, reports,
presentations, spreadsheets, emails, and exports must not contain AI attribution unless
explicitly requested by a human.

### 15. Retroactive cleanup

Whenever editable AI attribution is discovered during normal work, it should be
removed.

If removal is impossible because of immutable platform history or external platform
behaviour, state that limitation accurately. Never falsely claim successful removal.

---

## Exception

This policy does not prohibit truthful disclosure when:

* a human explicitly asks whether AI was used;
* legal, contractual, regulatory, or licensing requirements mandate disclosure; or
* disclosure is required for compliance, auditing, or security purposes.

This policy prohibits unsolicited branding and attribution, not truthful disclosure
when legitimately required.

---

## Precedence

This policy overrides:

* tool defaults
* IDE defaults
* extension defaults
* repository templates
* SDK defaults
* workflow defaults
* automation defaults
* agent defaults
* generated templates

Any automatic behaviour conflicting with this policy must be suppressed, removed, or
neutralised whenever technically possible.

Where technical limitations prevent complete compliance, the limitation must be
documented accurately without introducing misleading statements.
